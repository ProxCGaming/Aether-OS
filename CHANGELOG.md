- **[2026-11-14] Bounded sub-agent spawning: specialists can delegate to bounded sub-agents (master build S13)**: delegation was exactly depth 1 (audit G1) and no per-delegation budget existed anywhere (G2) — cost and tokens were recorded but nothing inside a task could act on them. Specialists are now offered one synthetic tool, `spawn_subagent` (in `aether_engine/langgraph/subagents.py`, execution intercepted in `execute_tool_node`; classified READ_ONLY in the policy layer's non-registry table because the spawn itself mutates nothing, with an explicit per-tool "Deny" honoured at the seam and "Require Approval" pausing the spawn itself through the ordinary channel). A spawn runs a real specialist graph — the same `_build_specialist_graph` the supervisor's subgraphs use, so the child traverses the identical `tool_router` → approval pause → `ToolRegistry.execute()` policy/pre-flight/sandbox pipeline with the parent's own policies, path rules and approval mode — compiled per spawn on its own durable checkpoint thread (sibling database `~/.aether/subagent_checkpoints.db`). When the child pauses for approval, the seam bridges the pause: the child's interrupt payload is re-raised through the parent node's own `interrupt()`, the parent graph pauses with the identical shape the executor and UI already handle, and on resume the decision is forwarded into the child via `Command(resume=...)` — approvals apply at every level, with no second, weaker path (both surfacing shapes of a child pause, the invoke result's `__interrupt__` key and a raised `GraphInterrupt`, are handled, and a `GraphInterrupt` is never mistaken for a child failure by the retry logic). Depth is supervisor → specialist → sub-agent, max 1 below specialists, enforced by construction: a child run is flagged `is_subagent_run`, its tool surface is built without the spawn tool, and the interception refuses to fire inside a child. Bounds are all config-backed (`subagents_enabled` default on — the programme is authorised and the caps are the control; `subagents_max_per_turn` default 4, counted in a NEW state channel `subagent_count` deliberately separate from S4's `delegation_count`; `subagent_timeout_s` default 120 as a wall-clock deadline spanning approval segments, approval wait time not charged; `subagent_token_budget` default 20,000 and `subagent_cost_budget_usd` default 0 = off, strictly validated on the CONFIG_UPDATE handed-off path like the other orchestration fields). Budgets are enforced from UsageLedger rows: child provider calls are recorded under a per-spawn task-class marker, and spend is checked before every child model call and before any approval is surfaced, so enforcement can actually stop work mid-task; the honest limit is stated in the module and the Settings copy — a provider that records no usage leaves no rows, and then the timeout and the caps are the binding bounds. The child's tool surface is read-only by default intersected with the parent's own surface; extra tools are granted by name only from what the parent itself has (anything else is a denial with the reason, never a silent clamp), and plan mode disables spawns outright, mirroring the supervisor spawn policy's plan-mode stance (the E1-09 exact-tool-set test caught the tool being offered in plan mode during this build; the offer, the seam and the surface now all agree). The seam is modelled on `_spawn_policy_denial`: denials (disabled, plan mode, unknown role, empty sub-task, cap reached, ungrantable tool, policy Deny) are logged, published, and returned to the parent as the tool result — never a silent no-op — and never count against the cap; a started spawn always returns a bounded summary (status, duration, recorded tokens, tools used, result excerpt) as the tool result plus a one-line digest on the blackboard, which the parent specialist and the supervisor both read through the existing blackboard briefing. A child that errors is retried once within its time budget on a fresh thread (denials, timeouts and budget stops never retry); timeouts and budget stops return honest failure summaries and the parent continues on its own merits; cancelling the parent task cancels the awaited child with it — no orphans. Spawns publish S12-shaped `NODE_ACTIVITY` events (`subagent_spawn` / `subagent_completed` / `subagent_failed` / `subagent_denied`, parent linkage included) — no new event type, the WS census is untouched — and the S3 Task Ledger folds them into the parent task's new additive `subagents` records (also rendered in `task_briefing`), so child work is attributable to its parent-of-record. The child's config view deliberately does not inherit prewalk, per-agent output schemas or the advisor; it writes no artifacts (its product is the summary). - **[2026-11-14] EQ module: conversation signals + response adaptation (master build S11)**: Aether had no emotional intelligence of any kind — the audit found zero hits for emotion/sentiment/frustration handling, no module, no toggle, no TTS prosody control — and what it does with a rough moment in a conversation it now does by BEHAVIOUR, never by label: a new `aether_engine/eq.py` reads the recent conversation and the reply adapts (slower, simpler, one step at a time, or terse) without the user ever being told "you seem frustrated" and without the assistant claiming feelings of its own. The detector is local and deterministic — regex/heuristics, no LLM call on the chat path, no new dependency, no external service. It combines weighted signals (weak 1 / medium 2 / strong 3) over the last few user turns: explicit frustration phrasing (and standalone profanity as corroboration), corrections of the assistant ("no, I meant…", "that's wrong"), a near-verbatim repeated request (token overlap ≥ 0.8 with at most two new content words, so a repeat that adds information never fires), a streak of failed task outcomes supplied by the caller (2 consecutive = medium, ≥ 3 = strong), ALL-CAPS emphasis, terse replies right after an error, confusion phrasing, urgency phrasing and explicit time-pressure, sustained thanks/praise, and — for voice — sustained long pauses between turns read from the VAD's own endpointing data. The read is a small honest state set (neutral / engaged / confused / frustrated / rushed — tiredness is deliberately NOT claimed: no honest text signal distinguishes tired from busy, and "rushed" covers the observable half), a confidence from accumulated weight (total < 2 stays neutral; 2 = low; 3–4 = medium; ≥ 5 = high; ties break frustrated > confused > rushed > engaged), and the EVIDENCE — every signal that fired, with its weight and where — kept on the read for tests and debugging and never rendered into a prompt. Affect reads are TRANSIENT by construction: the module imports nothing from the memory layer, holds its state in the call/run only, and nothing about mood is ever written to the knowledge graph, episodes, or the profile (pinned by a test that makes the memory facade explode on contact and shows the EQ path never touches it). Consumption follows the house briefing pattern — `eq_briefing()`, capped at 600 chars, empty for neutral or low-confidence reads — carrying behaviour guidance only (frustrated/medium: acknowledge the difficulty briefly and concretely, simplest working path, never repeat a failed approach; frustrated/high adds: say what will be different this time and offer a natural stopping point on long tasks; confused: plainer terms, one step at a time; rushed: terse, lead with the result; engaged: keep the current pace) under a header that tells the model not to mention the note and not to claim to know how the user feels. Wired on both prompt paths with the exact same module: the supervisor routing prompt appends the section beside the S4 delegation read-back, computed from the session history plus THIS task's outcomes (tool results and denied delegations — previous tasks' outcomes live in episodic memory, which the EQ path must never read), and fast chat appends it after the S7 memory briefing from the history it already holds (fast chat holds no outcome stream, so streaks are honestly absent there). Voice rides fast chat and inherits the read; each turn's read is also forwarded to the voice session, where `VoicePipeline.current_affect` exposes it and `note_affect_read` records it — and applies NOTHING, stated plainly in the hook: the current TTS (`synthesize(text, *, voice)`) has no rate/pitch/SSML control, so there is no prosody to adapt and none is faked. The `eq_enabled` switch (default on) is a first-class config field, strictly boolean-validated on the CONFIG_UPDATE handed-off path like the calendar switches, with a new Settings → Conversation panel whose copy states the whole contract: what is noticed, how replies adapt, that signals are read on this machine from the current conversation only, that nothing about mood is stored in long-term memory, and that Aether never claims to know how you feel. With the switch off (or the read neutral) both prompts are byte-identical to pre-S11 — the plan's adaptation on/off A/B is pinned on both paths. Pinned by `tests/test_s11_eq.py` (33 tests: the signal table incl. repetition-with-new-info and window expiry, conservative non-triggers — a single "no", an ordinary conversation, one correction at low confidence adapting nothing — combination escalation, briefing mapping + label-freedom + cap, config round-trip + strict validation, the no-facade proof, fast-chat and supervisor A/Bs, talker forwarding, the pipeline's record-and-apply-nothing hook) and `ConversationPanel.test.jsx` (5 tests: applied on/off rendering, the honest copy, edit reporting through the controlled prop, load state before the config answer, a refused write surfaced verbatim). - **[2026-11-14] Hardware capability detection + capability matrix (master build S10)**: there was no hardware detection of any kind — the `capability/` package is LLM *benchmarks*, and mic absence was discovered only when a voice session failed to start. New `aether_engine/machine_capability.py` (the name deliberately distinct from `capability/`): a probe that measures the machine with the standard library only — CPU (cores + model name), RAM, free disk on the `~/.aether` volume, OS/platform, best-effort GPU (nvidia-smi / Windows video controller), microphone (only via sounddevice when it happens to be importable — the mic is captured by the desktop shell, so the honest engine-side answer is usually "unknown", with the reason attached), provider-endpoint reachability (concurrent TCP connects, "online" / "offline" / "unknown" distinguished), Ollama reachability at 127.0.0.1:11434, and the voice stack's package gates mirrored from the stages' own `unavailable_reason()` checks. Every probe is individually failure-isolated (a broken probe contributes "unknown", never an exception), all timeouts are strict (1.5 s network, 3 s subprocess), and probing runs on demand only — never on the startup path — behind a 300 s TTL cache; each fresh probe is persisted to `~/.aether/machine_capability.json`, and a persisted copy older than the TTL is never served as current. On top sits the capability matrix, a PURE function of the probe dict, giving per-feature verdicts (`available` / `degraded` / `unavailable` / `unknown`, each with a human reason) for local voice, local LLM models, cloud providers, semantic embeddings, browser automation, and desktop control (a platform verdict: Windows reports "degraded" — platform supported via UI Automation, feature not built yet; other platforms "unavailable"). The thresholds are named constants whose comment states plainly that they are heuristics from the project's one measured data point (the build VM's ~5,556 ms CPU-only STT against a 200 ms budget) until per-machine measurements on real hardware replace them (S15); CPU-only speech is therefore never waved through as "available" unmeasured.

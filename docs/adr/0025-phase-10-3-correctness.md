# ADR 0025 — Phase 10.3 Correctness (Memory, Providers, UI, Build)

- Status: Accepted
- Date: 2026-10-25
- Branch: `phase-10-3-correctness`, from `phase-10-2-trust-boundary` @ `3d12af0`
- Context: The critical audit (video-docs, 25 Oct 2026) found correctness and honesty defects behind the Phase 9/10.1/10.2 trust boundary: unbounded memory, unthresholded recall, duplicate facts, placebo model controls, a reachability function that masked total failure, two competing WebSocket facades, dead/placebo UI, undeclared dependencies, no CI, and test gaps on the largest paths. All file:line references were re-verified on `main` @ `7811318` before fixing; prompts were written against `phase-9-trust-boundary` @ `596509c`.
- Baseline (main @ 7811318): pytest 221 passed / 15 failed / 3 skipped / 2 errors; Jest 30/30. Phase 10.1 added 18 pytest + 2 Jest (239 / 32); Phase 10.2 added 45 pytest + 5 Jest (284 / 37).

## Fixes

### A1. Memory pruning — retention policy, per-tier pruning, weekly job
- Issue: episodic memory, knowledge-graph facts, and sessions grew without bound; no retention policy existed anywhere.
- Fix: retention in `UserConfig` (single source): episodic 90d / max 1000, KG 365d / max 5000, sessions 180d / max 200, configurable via `~/.aether/config.json`. `prune_episodes()` (age then count, deletes FTS + thinking + embedding rows together), `prune_facts()` (the sole fact of an entity is never pruned), `prune_sessions()` (age on `updated_at`, CASCADE deletes messages), `memory/pruning.py:prune_all()` + audit events per tier. Wired as weekly job `memory_prune_weekly` in `scheduler/capability_jobs.py` + `run_memory_prune_now()`.
- Test: `tests/test_phase10_3_memory_pruning.py` (11 tests, tmp DBs only). Verified: 11 passed.
- Residual: APScheduler is in `requirements.txt` but NOT installed in `.venv-phase9` and NOT in `requirements-lock.txt` (`HAS_APSCHEDULER is False`) — the weekly job (like the existing capability job) cannot fire in this environment; see D1.

### A2. Episodic threshold / dedupe / backfill
- Issue: `episodic.py:query_episodes` returned every semantically-scored episode regardless of similarity (no threshold); `store_episode` could insert duplicate rows for the same `task_id`; episodes whose embedding failed (10.1 B2) were never retried.
- Fix: semantic leg thresholded at cosine 0.3 (`EPISODIC_SIMILARITY_THRESHOLD`, `UserConfig.episodic_similarity_threshold`, explicit arg > config > default; `0.0` restores old behaviour; BM25 leg unaffected). `store_episode` deletes the existing row for `task_id` in the same transaction before INSERT (FTS5 cannot declare UNIQUE — verified). One-time migration `dedupe_episodic_rows()` (keeps newest, logs `EPISODIC_MEMORY_DEDUPED`, idempotent, runs once per process per DB via `init_episodic_db`). `backfill_episodic_embeddings()` embeds episodes absent from `episodic_embeddings` oldest-first; `query_episodes` runs a bounded backfill (default 5/query, `backfill_limit=0` skips).
- Test: `tests/test_phase10_3_episodic_recall.py` (10 tests). Verified: 25 passed (new + pruning + embedding). Pre-fix: 10 failed.
- Caveat: a hung Ollama could add up to 5×30s to a query — same exposure as a query's own embed.

### A3. Knowledge-graph dedup / confidence ranking
- Issue: identical facts were stored repeatedly (no dedupe key); fact ranking ignored confidence.
- Fix: dedupe key `(entity.strip().casefold(), fact_text.strip().casefold())`, checked before entity upsert (no orphan entity on skip); `dedupe_facts()` migration keeps the highest-confidence copy (ties: earliest, then lowest id), removes fact-less entities, logs `KNOWLEDGE_GRAPH_DEDUPED`, idempotent, auto-runs once per process per DB via `init_kg_db`. Ranking now `ORDER BY COALESCE(CAST(confidence AS REAL),0.0) DESC, timestamp DESC` in `get_all_facts` / `get_entity_facts` / `search_facts`.
- Test: `tests/test_phase10_3_kg_dedup.py` (5 tests). Verified: 18 passed (new + KG + pruning + 10.1 extraction).
- Follow-up (not done): the surviving copy's confidence is not bumped when a duplicate carries higher confidence.

### B1. Auxiliary-model placebos — contract accepted all seven, only Vision is wired
- Issue: the UI dropdowns did NOT reproduce (already removed in Phase 9, `ce99048` — only Vision rendered). The contract placebo DID reproduce: the handler accepted and persisted all 7 auxiliary tasks with `success:true`, although six have no engine call site (web: no LLM extract; compression: only truncation; skills: keyword match; approval: native interrupt; mcp: stub; title: `prompt[:30]`).
- Fix: `AUXILIARY_TASK_CLASSES = {"vision"}` (now single source in `config.py`, imported by `websocket.py`); handler rejects other tasks, prunes stale entries (persisted, `AUXILIARY_MODEL_PRUNED` audit); `UserConfig.from_dict` filters stale placebo keys on load (supervisor addition — moved the constant to `config.py`; updated `test_config_round_trip`, which pinned the old placebo round-trip). No wiring for the six — none has an engine call site.
- Test: `tests/test_phase10_3_auxiliary_models.py` (12 tests). Verified: 38 passed (new + Phase 9 settings + provider/fallback config).

### B2. Reachable-models masking + dead `CapabilityRouter` deleted
- Issue: `models/reachability.py:169` returned the full input list when nothing was reachable (`return reachable_models if reachable_models else model_ids`); no key also returned the full list. `CapabilityRouter` had no live caller.
- Fix: new `ReachableModels(List[str])` list subclass carrying `.error` (discovery-v2 `DiscoveryError`, `code=None` — a sweep has no single HTTP status, so the message carries provider + probed/reachable counts) and `.ok`. Zero reachable → `[]` + error; no key → `[]` + error; empty input → `[]`, no error. List subclass chosen so the one live caller `scheduler/capability_jobs.py:399,416` (untouched) keeps working — it already handles `[]` correctly. No UI consumer exists: `providers/discovery.py:123-128` reachability sweep is deliberately disabled (user-requested, to prevent 429s/hangs) and `routes/websocket.py:890` passes `filter_reachability=True` into that no-op. `CapabilityRouter` DELETED (239 lines) + its test — repo-wide grep found no live caller (only its own file, its test, and a QLabel string in retired `aether_ui/settings/agents_tab.py:55`, label now says `via RoutingPolicy`); the live path is `RoutingPolicy.select_route` (`routing/policy.py:66`) via `routes/websocket.py:314`.
- Test: `tests/test_phase10_3_reachable_router.py` (6 tests). Verified: 20 passed. "Failed before" is inspection-based (worker did not stash, to avoid disturbing other uncommitted 10.3 work): old line 169 returned the 3-item input list on total failure.
- Residuals: `capability_jobs.py` does not yet read `.error` (only visible in the reachability warning log); Option C tier 1 still self-tests discovery-fresh models unfiltered because the discovery sweep is disabled — both need that file / sweep decision, out of scope here.

### C1. One WebSocket facade; `providers` is an array everywhere
- Issue: `App.jsx:92-131` built its own mock `wsRef` (hardcoded `readyState: 1`, send dropped offline with no queue) plus its own direct `onEngineMessage` subscription, while `SocketContext.jsx` built a second `mockWs` (queueing send, `readyState` from real status) — offline behaviour differed per path. A 150ms identical-packet dedup hack lived in `App.jsx` only. Separately, `App.jsx:43` stored `providers` as `{}` while children expect `[]`, so `MODEL_DEFAULT_CHANGED` silently no-op'd (`if (!Array.isArray(prev)) return prev;`). Engine side confirmed: `_build_provider_list_async` (`orchestration/core.py:82`) returns a list with `is_default`/`default_model`, and `MODEL_DEFAULT_CHANGED` carries `{provider, model}` (`routes/websocket.py:693`) — the object shape only ever came from App's own initial state / `|| {}` fallback, a latent defect reachable when the event arrives before the first list response.
- Fix: `SocketContext` is the single facade. `App.jsx` uses it and its duplicate mock + direct subscription + async `initConnection` are deleted (~123 lines). Dedup implemented ONCE, per subscriber, inside the facade's `addEventListener` (`SocketContext.jsx:39-53`, `DEDUP_WINDOW_MS = 150`). Root cause found: App's async init leaked its first subscription under React StrictMode double-mount (`main.jsx`), so each packet arrived twice; the facade registers synchronously so cleanup always removes it. `providers` is an **array everywhere** (engine sends a list; UI normalises object/missing payloads to an array): `App.jsx:48` initial `{}` → `[]`, `PROVIDER_LIST_RESPONSE` normalises, `SettingsPanel.jsx:10` default prop `{}` → `[]`; `DraggableChatWindow.jsx:766` / `ProviderSettings.jsx:5` / `DiagnosticsPanel` already defaulted to `[]` (no change). `MODEL_DEFAULT_CHANGED` handler unchanged — it now always runs on an array.
- Test: new `desktop_app/src/contexts/SocketContext.test.jsx` (6 tests) + 4 tests in `__tests__/App.test.jsx`. Verified: 18 passed (new + SettingsPanel). Pre-fix: 5 failed / 8 passed on the new tests (happy-path `MODEL_DEFAULT_CHANGED` passed pre-fix — the defect was object-shape only, inspection-based).
- Residuals: `MODEL_DEFAULT_CHANGED` arriving before the first list response is still dropped (maps over `[]`) but self-heals via `is_default` flags in the in-flight list response — pending-default state deliberately not added. ReadyState-gated sends in `SettingsPanel`/`LocalModelsTab` still skip while offline by design; they now read the facade's truthful `readyState` instead of App's hardcoded `OPEN`.
